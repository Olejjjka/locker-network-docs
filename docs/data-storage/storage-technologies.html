Определение технологий хранения данных

Определение сущностей и выбор технологий хранения данных​

В рамках проектируемой информационной системы «Платформа городской сети камер хранения с возможностью доставки вещей между локациями» рассматриваются как основные бизнес-сущности, так и служебные данные, необходимые для корректной работы системы.

Основная часть данных носит транзакционный характер, поскольку система ориентирована на выполнение большого количества небольших операций: создание бронирований, изменение статусов, оформление перемещений, проведение оплат и обработку обращений. При этом часть данных в дальнейшем может использоваться в аналитических целях, например для расчёта бизнес-показателей, анализа нагрузки и оценки популярности локаций.

В модели данных выделены две группы сущностей:

  • основные бизнес-сущности – пользователь, локация, ячейка хранения, бронирование, заказ на перемещение, оплата и обращение в поддержку;
  • служебные данные – история статусов, вложения и документы, события и аудит, а также записи об идемпотентности запросов.

Основные бизнес-сущности отражают ключевые пользовательские сценарии системы, а служебные данные обеспечивают корректность работы, поддержку, аудит и техническую устойчивость.

Пояснение к выбору​

При выборе технологий хранения дополнительно учитывались требования к доступности данных, изменчивости схемы и стоимости решений.

Для основных бизнес-сущностей проекта структура данных достаточно стабильна, а требования к надёжности и согласованности высокие. Поэтому в качестве базового решения выбрана реляционная БД. Такой вариант подходит для хранения пользователей, локаций, ячеек, бронирований, перемещений, оплат и обращений в поддержку.

Для бронирований, заказов на перемещение и истории статусов также может использоваться аналитический контур DWH, так как эти данные важны не только для операционной работы, но и для анализа бизнес-показателей.

Для событий и аудита выбрано отдельное хранилище Data Lake / Object Storage. Эти данные могут быстро расти по объёму, чаще всего дописываются и используются преимущественно для аналитики, расследования инцидентов и технического мониторинга. Для них допустима более гибкая структура и менее жёсткие требования к немедленной консистентности.

Почему часть служебных сущностей не включена во вторую таблицу​

Во второй таблице рассмотрены только те сущности, которые напрямую влияют на выбор технологий хранения данных в рамках MVP.

Служебные сущности «Вложения и документы» и «Запись об идемпотентности запроса» отдельно не включены в таблицу выбора технологий хранения по следующим причинам:

  • вложения и документы пока не детализированы как отдельный значимый контур MVP;
  • запись об идемпотентности относится к технической реализации API и не влияет на выбор основного хранилища бизнес-данных;
  • для MVP ключевой выбор делается между операционной реляционной БД, аналитическим контуром и объектным хранилищем для событий и аудита.

Итоговое решение​

Итоговый выбор технологий хранения для MVP:

Группа данныхРешение
Основные бизнес-сущностиРеляционная БД
Бронирования, перемещения и история статусов для аналитикиDWH
События и аудитData Lake / Object Storage
Бинарные вложения, если будут детализированы позжеObject Storage
Служебные записи идемпотентностиРеляционная БД или отдельное key-value-хранилище в зависимости от реализации

Для MVP основным операционным хранилищем является реляционная БД, так как она лучше всего соответствует транзакционной природе системы и требованиям к целостности данных.
