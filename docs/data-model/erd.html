Проектирование ERD

В рамках проектирования модели данных для системы «Платформа городской сети камер хранения с возможностью доставки вещей между локациями» были подготовлены три уровня ERD:

  • концептуальная модель;
  • логическая модель;
  • физическая модель.

Модели построены последовательно: от верхнеуровневого описания сущностей и связей до физической структуры данных с типами, ограничениями и решениями под PostgreSQL.

Концептуальная модель​

На концептуальном уровне выделены основные сущности предметной области и связи между ними. На этом уровне модель не содержит атрибутов, типов данных и технических ограничений.

Ключевые связи​

  • пользователь создаёт бронирования;
  • бронирование связано с текущей ячейкой хранения;
  • ячейка принадлежит локации;
  • из активного бронирования может быть создан заказ на перемещение;
  • заказ на перемещение связан с исходной и целевой ячейками;
  • платежи связаны с бронированием или заказом на перемещение;
  • обращения в поддержку могут быть связаны с бронированием или перемещением.

Основные решения логической модели​

Отдельная сущность хранения не выделяется​

Отдельная сущность Storage в модели не создаётся. Хранение рассматривается как этап жизненного цикла бронирования Booking.

Это позволяет не дублировать сущности и сохранять понятную связь:

User → Booking → Cell → Location

Статусы вынесены в справочники​

Для фиксированных наборов статусов используются отдельные справочники:

  • CellStatus;
  • BookingStatus;
  • TransferStatus;
  • PaymentStatus;
  • SupportRequestStatus.

Такой подход позволяет не хранить статусы строками в основных таблицах и поддерживать нормализованную структуру данных.

История статусов хранится отдельно​

Для бронирований и перемещений используются отдельные таблицы истории:

  • BookingStatusHistory;
  • TransferStatusHistory.

История нужна для отслеживания изменений статусов, анализа спорных ситуаций и поддержки пользователей.

Поле old_status_id является необязательным, потому что первая запись истории может не иметь предыдущего статуса.

Payment не содержит user_id​

В Payment отдельный user_id не хранится.

Пользователь определяется через связанные бизнес-объекты:

Payment → Booking → User
Payment → Transfer → Booking → User

Такое решение позволяет не дублировать данные и сохраняет нормализацию.

Transfer не содержит payment_status_id​

В Transfer не хранится отдельный статус оплаты.

Статус оплаты определяется через связанную сущность Payment. Это позволяет избежать дублирования и не хранить одно и то же состояние в двух местах.

СУБД​

В качестве целевой СУБД выбрана:

PostgreSQL 14+

PostgreSQL подходит для проекта, потому что основные данные имеют выраженную реляционную структуру, требуют транзакционности, внешних ключей и ограничений целостности.

Физические ограничения​

Transfer​

Для заказа на перемещение зафиксировано ограничение:

CHECK (source_cell_id <> target_cell_id)

Оно запрещает создавать перемещение из ячейки в саму себя.

Payment​

Для платежа используется ограничение:

CHECK exactly one of booking_id, transfer_id

Платёж должен быть связан либо с бронированием, либо с заказом на перемещение, но не с обоими объектами одновременно и не существовать вне бизнес-контекста.

SupportRequest​

Для обращения в поддержку используется ограничение:

CHECK not both booking_id and transfer_id

Обращение может быть:

  • связано только с бронированием;
  • связано только с заказом на перемещение;
  • общим обращением без связи с конкретным объектом.

Но одно обращение не должно одновременно ссылаться и на бронирование, и на перемещение.

Краткое обоснование ключевых решений​

Модель данных построена на трёх уровнях:

  • на концептуальном уровне выделены основные сущности предметной области и связи между ними;
  • на логическом уровне добавлены атрибуты, PK/FK, бизнес-ограничения, справочники статусов и таблицы истории изменений;
  • на физическом уровне выбраны типы данных и ограничения для PostgreSQL.

Для основных бизнес-сущностей используются UUID, так как эти сущности могут создаваться независимо и использоваться во внешних API. Для статусных справочников выбран SMALLINT, потому что количество статусов ограничено и изменяется редко. Для таблиц истории используется BIGSERIAL, так как такие таблицы растут быстрее и записи в них в основном дописываются.

Дополнительные физические оптимизации, такие как денормализация, партиционирование и summary-таблицы, в модель не вводились. Для MVP это не требуется по текущим объёмам данных и нефункциональным требованиям.

Итог​

ERD-модель согласована с остальными артефактами проекта:

  • с требованиями и бизнес-правилами;
  • с API-структурой;
  • с жизненными циклами бронирования и перемещения;
  • с решением по хранению данных;
  • с выбранной физической СУБД PostgreSQL.

Модель сохраняет нормализованную структуру и не добавляет лишние связи, которые могли бы привести к дублированию данных.
