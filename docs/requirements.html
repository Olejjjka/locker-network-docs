Требования

Раздел содержит функциональные и нефункциональные требования к проектируемой системе.

Функциональные требования описаны в формате use case-сценариев. Нефункциональные требования сгруппированы по категориям качества: безопасность, производительность, надёжность, наблюдаемость, удобство использования, совместимость, нормативные требования, ёмкость, масштабируемость и поддерживаемость.

Функциональные требования​

UC-1 – Регистрация пользователя​

РазделОписание
IDUC-1
НазваниеРегистрация пользователя
АкторыПользователь
Предусловия1. Пользователь имеет доступ к Интернету
2. Пользователь не авторизован в системе
3. Платформа доступна и функционирует в штатном режиме
Основной поток1. Пользователь открывает раздел «Регистрация» на платформе
2. Система отображает форму регистрации с полями ввода данных: имя, номер телефона, пароль и подтверждение пароля
3. Пользователь вводит регистрационные данные
4. Пользователь подтверждает согласие с политикой обработки персональных данных
5. Пользователь нажимает кнопку «Зарегистрироваться»
6. Система проверяет корректность введённых данных:
- все обязательные поля заполнены
- формат номера телефона корректен и номер не зарегистрирован ранее
- пароль соответствует требованиям безопасности
7. При успешной проверке данных система отправляет SMS с кодом подтверждения на указанный номер телефона и отображает поле для ввода кода
8. Пользователь вводит полученный код подтверждения
9. Система проверяет корректность кода подтверждения
10. При успешной проверке система создаёт учётную запись пользователя
11. Система отображает сообщение об успешной регистрации
Постусловия (успех)1. В системе создана новая учётная запись пользователя
2. Пользователь может перейти к авторизации в системе
Постусловия (неудача)1. Учётная запись не создана
2. Пользователь получает сообщение о причине ошибки регистрации
Альтернативные потоки6а. Если данные заполнены некорректно – система отображает сообщение об ошибке и предлагает исправить данные
6б. Если номер телефона уже используется – система уведомляет пользователя и предлагает выполнить вход или восстановить пароль
7а. Если SMS-код не доставлен – пользователь может запросить повторную отправку кода
9а. Если код подтверждения введён неверно – система предлагает повторить ввод кода с ограничением количества попыток
Бизнес-правилаBR-1. Номер телефона должен быть уникальным в системе
BR-2. Пароль должен содержать допустимое количество символов и удовлетворять требованиям безопасности
BR-3. Код подтверждения имеет ограниченный срок действия
BR-4. Количество попыток ввода кода подтверждения ограничено
BR-5. Учётная запись пользователя получает статус «активна» после успешного подтверждения SMS-кода

UC-2 – Авторизация пользователя​

РазделОписание
IDUC-2
НазваниеАвторизация пользователя
АкторыПользователь
Предусловия1. Пользователь имеет доступ к Интернету
2. Пользователь зарегистрирован в системе и учётная запись активна
3. Платформа доступна и функционирует в штатном режиме
Основной поток1. Пользователь открывает раздел «Вход» на платформе
2. Система отображает форму авторизации с полями ввода данных: номер телефона и пароль
3. Пользователь вводит учётные данные
4. Пользователь нажимает кнопку «Войти»
5. Система проверяет корректность введённых данных:
- в системе существует учётная запись с указанным номером телефона
- введённый пароль соответствует паролю учётной записи пользователя
6. При успешной проверке система предоставляет пользователю доступ к личному кабинету и основным функциям платформы
Постусловия (успех)1. Пользователь авторизован в системе
2. Пользователь получает доступ к функциям бронирования, хранения вещей и поддержке
Постусловия (неудача)1. Доступ к системе не предоставлен
2. Пользователь получает сообщение об ошибке авторизации
Альтернативные потоки5а. Если номер телефона не зарегистрирован в системе – система сообщает об отсутствии учётной записи
5б. Если пароль введён неверно – система отображает сообщение об ошибке и отображает возможность восстановления пароля
5в. Если превышено допустимое количество попыток входа – система временно блокирует доступ к аккаунту
Бизнес-правилаBR-1. Авторизация разрешена только для активных учётных записей пользователей
BR-2. Сессия пользователя имеет ограниченное время действия
BR-3. После нескольких неудачных попыток входа доступ к аккаунту может быть временно ограничен
BR-4. Доступ к функционалу платформы предоставляется только после успешной аутентификации пользователя

UC-3 – Поиск и бронирование камеры хранения​

РазделОписание
IDUC-3
НазваниеПоиск и бронирование камеры хранения
АкторыПользователь (авторизованный)
Внешний картографический сервис через API-интеграцию
Предусловия1. Пользователь имеет доступ к Интернету
2. Пользователь авторизован в системе
3. Платформа доступна и функционирует в штатном режиме
4. В системе присутствуют доступные камеры хранения
Основной поток1. Пользователь открывает раздел поиска камер хранения
2. Система загружает карту через внешний картографический сервис
3. Система отображает расположение камер хранения на карте города
4. Пользователь выбирает интересующую локацию камеры хранения или использует поиск по адресу
5. Система отображает информацию о выбранной камере хранения, включая:
- наличие свободных ячеек
- размеры доступных ячеек
- стоимость хранения
6. Пользователь выбирает размер ячейки и предполагаемый срок хранения
7. Система проверяет наличие свободной ячейки выбранного типа на указанный срок хранения и автоматически рассчитывает стоимость услуги
8. Пользователь проверяет рассчитанную стоимость и нажимает кнопку «Забронировать»
9. При успешной проверке система резервирует ячейку на ограниченный период времени за пользователем
10. Система отображает подтверждение бронирования и номер резервирования
Постусловия (успех)1. Камера хранения забронирована за пользователем
2. Информация о бронировании отображается в личном кабинете
3. Ячейка камеры хранения резервируется на ограниченный период времени до подтверждения размещения вещей
Постусловия (неудача)1. Бронирование не создано
2. Пользователь получает сообщение о невозможности резервирования выбранной ячейки
Альтернативные потоки2а. Если внешний картографический сервис не отвечает в течение заданного времени, система отображает последнюю доступную карту и уведомляет пользователя о проблеме соединения
4а. Если камера хранения, выбранная пользователем, временно недоступна – система отображает сообщение о временной недоступности локации и предлагает выбрать другую точку хранения
7а. Если выбранный тип ячейки недоступен на указанный срок хранения – система предлагает пользователю скорректировать параметры бронирования
Бизнес-правилаBR-1. Бронирование камеры хранения доступно только для авторизованных пользователей с активной учётной записью
BR-2. Если пользователь не подтвердил размещение вещей в камере хранения в течение установленного времени резервирования, бронирование автоматически отменяется, а ячейка возвращается в пул доступных ресурсов

UC-4 – Сдача вещей в камеру хранения​

РазделОписание
IDUC-4
НазваниеСдача вещей в камеру хранения
АкторыПользователь (авторизованный)
Сервис контроля доступа камеры хранения
Предусловия1. Пользователь имеет доступ к Интернету
2. Пользователь авторизован в системе
3. Пользователь имеет активное бронирование камеры хранения
4. Платформа доступна и функционирует в штатном режиме
Основной поток1. Пользователь открывает раздел текущего бронирования
2. Система отображает информацию о забронированной ячейке и сроке хранения
3. Пользователь подходит к физической камере хранения
4. Пользователь подтверждает намерение разместить вещи в камере хранения через платформу, например с помощью QR-кода или кода подтверждения
5. Сервис контроля доступа камеры хранения выполняет проверку права пользователя на доступ к ячейке
6. При успешной проверке система открывает выбранную ячейку камеры хранения
7. Пользователь размещает вещи в ячейке
8. Пользователь закрывает ячейку камеры хранения
9. Система фиксирует факт начала хранения вещей и изменяет статус бронирования на «Активное хранение»
Постусловия (успех)1. Вещи пользователя размещены в камере хранения
2. Статус бронирования изменён на «Активное хранение»
3. Зафиксировано начало периода хранения
Постусловия (неудача)1. Доступ к ячейке не предоставлен
2. Пользователь получает сообщение о невозможности открыть камеру хранения
Альтернативные потоки4а. Если подтверждение размещения вещей не выполнено – система предлагает повторить попытку
5а. Если проверка права доступа не пройдена – система уведомляет пользователя об ошибке доступа
6а. Если система контроля доступа не смогла открыть ячейку – система предлагает обратиться в службу поддержки, если повторная попытка открытия ячейки невозможна
Бизнес-правилаBR-1. Доступ к ячейке предоставляется только при наличии активного бронирования
BR-2. Факт начала хранения фиксируется системой после закрытия ячейки
BR-3. Открытие ячейки осуществляется через систему контроля доступа платформы

НазваниеЗаказ перемещения вещей между локациями

Внешний картографический сервис через API-интеграцию
Служба доставки вещей
Предусловия1. Пользователь имеет доступ к Интернету
2. Пользователь авторизован в системе
3. Пользователь имеет активное хранение вещей в камере хранения
4. Платформа доступна и функционирует в штатном режиме
Основной поток1. Пользователь открывает раздел управления хранением вещей
2. Система отображает информацию о текущем хранении
3. Пользователь выбирает опцию «Заказать перемещение вещей»
4. Система загружает карту через внешний картографический сервис
5. Система отображает расположение камер хранения на карте города
6. Пользователь выбирает целевую локацию камеры хранения для доставки вещей или использует поиск по адресу
7. Система проверяет возможность перемещения вещей между выбранными локациями
8. Система рассчитывает стоимость доставки вещей
9. Пользователь проверяет стоимость доставки и подтверждает заказ перемещения
10. Система фиксирует заказ доставки вещей
11. Служба доставки получает информацию о заказе перемещения
12. Система изменяет статус хранения вещей на «В процессе перемещения»
Постусловия (успех)1. Создан заказ на перемещение вещей
2. Начат процесс доставки вещей между локациями
3. Статус хранения изменён на «В процессе перемещения»
Постусловия (неудача)1. Заказ на перемещение не создан
2. Пользователь получает сообщение о невозможности выполнения доставки
Альтернативные потоки4а. Если внешний картографический сервис не отвечает в течение заданного времени, система отображает последнюю доступную карту и уведомляет пользователя о проблеме соединения
7а. Если перемещение вещей между выбранными локациями невозможно – система предлагает выбрать другую точку доставки или завершить процесс заказа перемещения
9а. Если пользователь отменяет подтверждение заказа перемещения – система не фиксирует заказ доставки и процесс завершается
Бизнес-правилаBR-1. Перемещение вещей возможно только при активном хранении
BR-2. Пользователь обязан подтвердить стоимость доставки перед оформлением заказа
BR-3. Перемещение вещей осуществляется только между подключёнными локациями сети
BR-4. Стоимость доставки рассчитывается автоматически
BR-5. Перемещение вещей выполняется через службу доставки платформы
BR-6. При заказе перемещения вещей срок хранения остаётся неизменным

UC-6 – Оплата услуг хранения и доставки​

РазделОписание
IDUC-6
НазваниеОплата услуг хранения и доставки
АкторыПользователь (авторизованный)
Платёжный шлюз (внешний сервис оплаты)
Предусловия1. Пользователь имеет доступ к Интернету
2. Пользователь авторизован в системе
3. Пользователь имеет активную услугу хранения или заказа перемещения вещей
4. Платформа доступна и функционирует в штатном режиме
5. Система рассчитала стоимость услуги
Основной поток1. Пользователь открывает раздел оплаты услуг
2. Система отображает информацию о стоимости услуг хранения или доставки
3. Пользователь выбирает способ оплаты
4. Пользователь подтверждает оплату услуг
5. Система передаёт платёжные данные во внешний платёжный шлюз
6. Платёжный шлюз выполняет обработку платежа
7. При успешной оплате система фиксирует транзакцию
8. Система изменяет статус услуги на «Оплачено»
9. Пользователю отображается подтверждение оплаты
Постусловия (успех)1. Оплата услуг успешно выполнена
2. Транзакция сохранена в системе
3. Статус услуги изменён на «Оплачено»
Постусловия (неудача)1. Оплата не выполнена
2. Пользователю отображается сообщение об ошибке оплаты
3. Система не изменяет статус услуги
Альтернативные потоки5а. Если платёжный шлюз недоступен – система уведомляет пользователя и предлагает повторить попытку оплаты или выбрать другой способ оплаты
7а. Если платёж отклонён – система отображает сообщение о невозможности завершения операции
8а. Если пользователь отменяет оплату – транзакция не фиксируется
Бизнес-правилаBR-1. Оплата услуг должна быть выполнена в соответствии с условиями тарификации перед предоставлением доступа к платным операциям
BR-2. Система поддерживает только разрешённые способы оплаты
BR-3. Финансовые операции выполняются через внешний платёжный шлюз
BR-4. Статус услуги изменяется только после подтверждения успешной оплаты
BR-5. Все финансовые транзакции должны быть сохранены в системе
BR-6. При превышении оплаченного периода хранения система может формировать задолженность пользователя

UC-7 – Завершение хранения вещей​

РазделОписание
IDUC-7
НазваниеЗавершение хранения вещей
АкторыПользователь (авторизованный)
Сервис контроля доступа камеры хранения
Предусловия1. Пользователь имеет доступ к Интернету
2. Пользователь авторизован в системе
3. Пользователь имеет активное хранение вещей и право доступа к ячейке хранения
4. Платформа доступна и функционирует в штатном режиме
Основной поток1. Пользователь открывает раздел текущего хранения вещей

4. Пользователь подтверждает намерение завершить хранение через платформу, например с помощью QR-кода или кода подтверждения
5. Сервис контроля доступа камеры хранения выполняет проверку права пользователя на доступ к ячейке
6. При успешной проверке система открывает ячейку камеры хранения
7. Пользователь забирает вещи из ячейки
8. Пользователь закрывает ячейку камеры хранения
9. Система фиксирует факт завершения хранения и изменяет статус бронирования на «Хранение завершено»
Постусловия (успех)1. Хранение вещей завершено
2. Статус бронирования изменён на «Хранение завершено»
3. Доступ к ячейке прекращён
Постусловия (неудача)1. Завершение хранения не выполнено
2. Пользователь получает сообщение о невозможности завершить хранение
Альтернативные потоки4а. Если проверка права доступа не пройдена – система сообщает об ошибке доступа
6а. Если ячейка не открылась – система предлагает обратиться в службу поддержки
7а. Если пользователь не забрал вещи в течение установленного времени – система может ограничить доступ к ячейке и сформировать задолженность
Бизнес-правилаBR-1. Завершение хранения возможно только при активном хранении вещей
BR-2. Открытие ячейки осуществляется через систему контроля доступа платформы
BR-3. Финансовые начисления за хранение прекращаются после фиксации завершения хранения
BR-4. При превышении оплаченного периода хранения может формироваться задолженность пользователя

Нефункциональные требования​

Безопасность (Security)​

NFR-1​

Название: Защита персональных данных пользователей

Описание:

  • передача данных между клиентом и сервером должна осуществляться по защищённому протоколу HTTPS с использованием TLS 1.2 или выше;
  • пароли пользователей должны храниться в виде криптографического хеша с использованием устойчивых алгоритмов, например bcrypt или Argon2;
  • допускается не более 5 неудачных попыток авторизации подряд, после чего аккаунт блокируется на 15 минут;
  • резервные копии, содержащие персональные данные, должны храниться в зашифрованном виде.

Приоритет: Must Have

Обоснование: платформа обрабатывает персональные и финансовые данные пользователей. Нарушение требований безопасности может привести к утечке информации, финансовым потерям и юридической ответственности.

NFR-2​

Название: Аутентификация и авторизация

Описание:

  • все операции, связанные с бронированием, оплатой, получением и завершением хранения, доступны только после успешной аутентификации пользователя;
  • аутентификация должна осуществляться с использованием токенов доступа, например JWT;
  • срок жизни токена доступа составляет не более 30 минут;
  • при отсутствии активности пользователя в течение 30 минут требуется повторная аутентификация;
  • система должна реализовывать ролевую модель доступа;
  • минимальные роли: пользователь, администратор, сотрудник поддержки;
  • доступ к административным функциям должен предоставляться строго в соответствии с назначенной ролью;
  • система должна реализовывать принцип наименьших привилегий: пользователь имеет доступ только к своим данным и операциям;
  • попытки несанкционированного доступа должны фиксироваться в журнале безопасности.

Приоритет: Must Have

Обоснование: система управляет финансовыми транзакциями и физическим доступом к камерам хранения. Некорректная реализация аутентификации и авторизации может привести к несанкционированному доступу к вещам пользователей и административному функционалу.

Производительность (Performance)​

NFR-3​

Название: Время отклика системы

Описание: среднее время ответа API для операций поиска, бронирования и оплаты должно быть ≤ 2 секунды для 95% запросов.

Приоритет: Must Have

Обоснование: быстрая работа интерфейса критически важна для пользовательского опыта.

NFR-4​

Название: Параллельная обработка запросов

Описание:

  • система должна поддерживать параллельную обработку пользовательских запросов;
  • поддержка не менее 500 одновременно активных пользователей;
  • пиковая нагрузка – до 100 RPS для MVP.

Приоритет: Must Have

Обоснование: требуется для стабильной работы при росте пользовательской активности.

NFR-5​

Название: Ограничение использования серверных ресурсов

Описание:

  • средняя загрузка CPU серверного узла при нормальной нагрузке до 100 RPS не должна превышать 70%;
  • использование оперативной памяти не должно превышать 80% доступного объёма.

Приоритет: Should Have

Обоснование: позволяет обеспечить стабильность системы и избежать деградации производительности.

Надёжность (Reliability)​

NFR-6​

Название: Доступность системы

Описание:

  • доступность платформы должна составлять не менее 99% в месяц;
  • допустимое время простоя системы – не более 7 часов в месяц;
  • время восстановления после сбоя (MTTR) – не более 30 минут.

Приоритет: Must Have

Обоснование: платформа является сервисом управления хранением вещей.

Наблюдаемость (Observability)​

NFR-7​

Название: Мониторинг и логирование

Описание:

  • логирование всех критических операций пользователя: регистрация, авторизация, бронирование, оплата, операции контроля доступа;
  • хранение логов – минимум 90 дней;
  • обнаружение критических ошибок должно приводить к автоматическому уведомлению службы поддержки в течение 5 минут.

Приоритет: Should Have

Обоснование: требуется для технической поддержки и диагностики инцидентов.

Удобство использования (Usability)​

NFR-8​

Название: Пользовательский интерфейс

Описание:

  • основные операции платформы должны выполняться не более чем за 5 шагов;
  • среднее время выполнения операции бронирования – не более 3 минут для нового пользователя;
  • не менее 80% новых пользователей должны успешно выполнить бронирование без обращения в поддержку;
  • интерфейс должен быть адаптивным для экранов от 320px до 2560px.

Приоритет: Must Have

Обоснование: целевая аудитория сервиса включает пользователей с разным уровнем технической подготовки.

Совместимость (Compatibility)​

NFR-9​

Название: Поддержка браузеров и устройств

Описание:

  • платформа должна корректно функционировать в последних 2 версиях следующих браузеров: Google Chrome, Mozilla Firefox, Safari, Яндекс Браузер;
  • система должна поддерживать работу на мобильных устройствах под управлением iOS и Android через современные мобильные браузеры;
  • поддержка устаревших браузеров, Internet Explorer и версии старше 3 лет не гарантируется.

Приоритет: Should Have

Обоснование: целевая аудитория использует различные устройства и браузеры. Обеспечение совместимости с основными современными платформами минимизирует технические барьеры входа и снижает количество пользовательских инцидентов.

Нормативно-правовые требования (Regulatory)​

NFR-10​

Название: Соответствие законодательству

Описание:

  • система должна обеспечивать защиту персональных данных пользователей в соответствии с действующим законодательством;
  • финансовые операции должны проводиться через защищённые платёжные сервисы;
  • хранение персональных данных пользователей должно осуществляться на защищённых серверах;
  • обработка данных должна соответствовать требованиям действующего законодательства о персональных данных.

Приоритет: Must Have

Обоснование: на этапе MVP допускается реализация базовых механизмов соответствия нормативным требованиям.

Ёмкость (Capacity)​

Почему категория не критична для MVP?​

На этапе MVP система рассчитана на ограниченный масштаб эксплуатации:

  • до 10 000 зарегистрированных пользователей;
  • до 500 одновременно активных пользователей;
  • хранение истории операций не более 1 года;
  • отсутствие загрузки пользовательских файлов и медиа-контента.

Основные данные представляют собой транзакционные записи: бронирование, хранение, оплата. Объём этих данных прогнозируется как умеренный и линейно растущий.

Таким образом, на этапе MVP не ожидается экстремального роста объёмов данных, требующего сложной стратегии управления ёмкостью.

Риски игнорирования​

  • переполнение базы данных при росте аудитории;
  • снижение производительности запросов;
  • увеличение времени резервного копирования;
  • рост затрат на инфраструктуру.

Планируется ли добавление в будущих версиях?​

Да, при развитии платформы планируется:

  • введение политики архивирования данных старше 1 года;
  • ограничение на хранение исторических логов;
  • детализация требований к объёму БД, например поддержка до 1 млн пользователей;
  • использование партиционирования и оптимизации индексов.

Масштабируемость (Scalability)​

Почему категория не критична для MVP?​

Для MVP предполагается ограниченная география запуска – пилотный город. Это снижает требования к масштабированию инфраструктуры.

Риски игнорирования​

  • невозможность быстрого роста при успешном запуске;
  • ограничение расширения на новые города;
  • риск деградации системы при превышении 100 RPS;
  • необходимость срочной переработки архитектуры.

Планируется ли добавление в будущих версиях?​

Да, при развитии платформы планируется:

  • реализация полноценного горизонтального масштабирования;
  • балансировка нагрузки;
  • поддержка нагрузки от 1000+ RPS.

Поддерживаемость (Maintainability)​

Почему категория не критична для MVP?​

MVP разрабатывается небольшой командой в рамках ограниченного цикла разработки.

Архитектура системы не предполагает высокой сложности на этапе запуска.

Ключевой приоритет MVP – проверка бизнес-гипотезы, а не долгосрочная оптимизация сопровождения.

Риски игнорирования​

  • увеличение технического долга;
  • усложнение внедрения новых функций;
  • повышение времени исправления ошибок;
  • зависимость от конкретных разработчиков.

Планируется ли добавление в будущих версиях?​

Да, при переходе к промышленной эксплуатации планируется:

  • введение требований к покрытию автотестами не менее 70%;
  • код-ревью и стандарты кодирования.
