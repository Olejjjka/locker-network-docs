# Style Guide

## Назначение

Данный раздел описывает правила оформления технической документации проекта **«Платформа городской сети камер хранения с возможностью доставки вещей между локациями»**.

Style Guide нужен для того, чтобы документация оставалась единообразной, понятной и удобной для дальнейшего сопровождения.

## Общие принципы

Документация ведётся в подходе **Doc as Code**:

- документы хранятся в репозитории вместе с проектом документации;
- основной формат документов – Markdown / MDX;
- изменения фиксируются через Git;
- сайт документации собирается через Docusaurus;
- опубликованная версия доступна через GitHub Pages.

## Структура документации

Документация размещается в папке:

```text
my-website/docs/
```

Основные разделы:

```text
docs/
├── intro.mdx
├── product/
├── requirements/
├── processes/
├── uml/
├── api/
├── async/
├── data-storage/
├── data-model/
├── platformization/
├── style-guide/
└── templates/
```

Каждый раздел должен отвечать за один тип артефактов:

| Раздел | Назначение |
| ------ | ---------- |
| `product` | Концепция, границы проекта и описание MVP |
| `requirements` | Требования и сбор требований |
| `processes` | BPMN, DMN и бизнес-процессы |
| `uml` | UML-диаграммы |
| `api` | API по макетам и OpenAPI |
| `async` | Асинхронное взаимодействие и AsyncAPI |
| `data-storage` | Выбор технологий хранения данных |
| `data-model` | ERD и модель данных |
| `platformization` | Платформизация проекта |
| `style-guide` | Правила ведения документации |
| `templates` | Шаблоны недостающих артефактов |

## Frontmatter

Каждый Markdown-файл должен начинаться с блока frontmatter:

```markdown
---
title: Название страницы
sidebar_position: 1
description: Краткое описание страницы
---
```

Поля:

| Поле | Назначение |
| ---- | ---------- |
| `title` | Название страницы в Docusaurus |
| `sidebar_position` | Порядок страницы внутри раздела |
| `description` | Краткое описание страницы |

## Заголовки

На странице должен быть один заголовок первого уровня:

```markdown
# Название страницы
```

Дальше используются заголовки второго и третьего уровня:

```markdown
## Раздел

### Подраздел
```

Не рекомендуется пропускать уровни заголовков, например переходить сразу от `##` к `####`.

## Именование файлов

Файлы и папки называются латиницей, в нижнем регистре.

Для разделения слов используется дефис:

```text
api-by-wireframes.md
storage-technologies.md
missing-artifacts.md
```

Не рекомендуется использовать:

- пробелы;
- русские буквы;
- кавычки;
- длинные имена файлов;
- специальные символы.

## Изображения

Изображения размещаются в папке:

```text
my-website/static/img/
```

Пример структуры:

```text
static/img/
├── api/
├── erd/
├── bpmn/
└── requirements/
```

Подключение изображения в Markdown:

```markdown
![Описание изображения](/img/api/api-wireframes.png)
```

Для изображений нужно использовать понятное описание, чтобы по нему было ясно, что изображено на схеме.

## Файлы для скачивания

Исходные файлы диаграмм и спецификаций размещаются в папке:

```text
my-website/static/files/
```

Пример:

```text
static/files/
├── bpmn/
├── asyncapi/
└── drawio/
```

Ссылка на файл:

```markdown
[BPMN-файл](/files/bpmn/business-process-transfer.bpmn)
```

## Диаграммы

В проекте могут использоваться несколько форматов диаграмм:

| Формат | Использование |
| ------ | ------------- |
| PNG / SVG | Для стабильного отображения готовых схем |
| PlantUML | Для UML- и sequence-диаграмм прямо в Markdown |
| draw.io XML | Для хранения редактируемых исходников схем |
| BPMN / DMN | Для бизнес-процессов и таблиц решений |

Если схема важна для просмотра, рекомендуется добавлять PNG-превью. Если схема должна редактироваться позже, рядом можно хранить исходный файл.

## OpenAPI

OpenAPI-спецификация хранится в папке:

```text
my-website/static/openapi/openapi.yaml
```

Она подключается через `redocusaurus` и отображается в отдельном разделе сайта:

```text
/api/openapi
```

В Markdown-страницах на неё можно ссылаться так:

```markdown
[OpenAPI](/api/openapi)
```

## AsyncAPI

AsyncAPI-спецификация хранится как исходный файл:

```text
my-website/static/files/asyncapi/AsyncAPI.yaml
```

На странице асинхронного взаимодействия нужно указывать:

- выбранный сценарий;
- технологию взаимодействия;
- формат сообщений;
- команду подписки;
- событие, которое отправляет backend;
- ссылку на исходный AsyncAPI-файл.

## Ссылки

Внутренние ссылки на страницы документации лучше указывать с относительным путём:

```markdown
[Требования](../requirements/requirements.md)
```

Ссылки на файлы из `static` начинаются с `/`:

```markdown
[Файл](/files/asyncapi/AsyncAPI.yaml)
```

Не нужно вручную добавлять `/locker-network-docs/` в ссылки. Docusaurus сам учитывает `baseUrl`.

## Стиль текста

Текст документации должен быть:

- понятным;
- структурированным;
- без лишней канцелярщины;
- с короткими абзацами;
- с таблицами там, где они повышают читаемость;
- с едиными терминами по всему проекту.

В документации используются согласованные термины:

| Термин | Использование |
| ------ | ------------- |
| Бронирование | Объект `Booking`, через который сопровождается хранение |
| Перемещение | Заказ `Transfer` на доставку вещи между локациями |
| Ячейка | Физическая ячейка хранения, объект `Cell` |
| Локация | Точка городской сети камер хранения |
| Обращение | Запрос пользователя в поддержку |
| Платёж | Объект `Payment`, связанный с бронированием или перемещением |

## Оформление статусов

Статусы бизнес-сущностей пишутся в кодовом формате:

```text
ACTIVE_STORAGE
WAITING_FOR_COURIER_ASSIGNMENT
ITEM_PICKED_UP
INCIDENT
```

Если нужно пояснение, оно добавляется рядом:

```markdown
`WAITING_FOR_COURIER_ASSIGNMENT` – ожидание назначения курьера
```

## Проверка перед публикацией

Перед коммитом нужно выполнить сборку:

```powershell
npm run build
```

Если сборка проходит без ошибок, документацию можно коммитить и отправлять в репозиторий.

## Коммиты

Для изменений в документации рекомендуется использовать понятные сообщения коммитов:

```text
docs: добавить раздел требований
docs: обновить ERD
docs: добавить OpenAPI спецификацию
docs: настроить GitHub Pages
```

## Что не рекомендуется

Не рекомендуется:

- хранить важные диаграммы только во внешних сервисах без копии в репозитории;
- использовать русские имена файлов для картинок и исходников;
- дублировать один и тот же артефакт в нескольких разделах;
- вставлять слишком большие блоки текста без заголовков;
- добавлять ссылки на локальные файлы компьютера;
- вручную прописывать `/locker-network-docs/` в путях к изображениям и файлам.
